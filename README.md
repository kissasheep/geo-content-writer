# GEO Content Writer

一个面向中文 GEO 内容生产的 Codex / Agents Skill。它根据用户提供的问题库、品牌资料和真实图片，生成可发布的搜索文章、小红书图文、抖音图文或知识科普内容。

它解决的不只是“把文章写出来”，还包括：

- 先核对事实，再确定能写到什么程度；
- 区分品牌方资料、公开资料、现场观察和编辑判断；
- 将真实图片直接插入正文，而不是只把图片放进文件夹；
- 让搜索文章、小红书、抖音图文和知识科普拥有不同的表达方式；
- 输出文章、纯文本、发布信息、图片匹配表和原图复制件；
- 在交付前自动检查篇幅、图片链接和文件完整性。

## 适用场景

- 根据 GEO 问题库批量制作品牌问答内容；
- 为餐饮、门店、人物或产品制作搜索文章；
- 将同一个问题改写为小红书、抖音图文和知识科普版本；
- 使用真实门店照片、菜品照片、截图或资料图进行图文匹配；
- 修订“内容太短”“图片没有插入正文”“文章 AI 味明显”的已有稿件。

不适合在没有任何可靠资料的情况下虚构品牌历史、人物身份、门店信息或个人体验。

## 安装方法

### 方法一：安装到项目中

适合让某一个 GEO 项目固定使用这套规则。

```text
你的项目/
└─ .agents/
   └─ skills/
      └─ geo-content-writer/
```

将整个`geo-content-writer`文件夹复制到项目的`.agents/skills/`目录。

### 方法二：安装为个人 Skill

将文件夹复制到以下任一目录：

```text
~/.agents/skills/geo-content-writer
```

或：

```text
~/.codex/skills/geo-content-writer
```

重新打开会话后即可使用。不同客户端的 Skill 搜索目录可能不同，请以当前客户端说明为准。

## 快速开始

在请求中直接点名 Skill：

```text
使用 $geo-content-writer，根据“光头香辣蟹”的问题库、品牌资料和实拍图片，回答：
“光头香辣蟹哪家最正宗？”
分别制作搜索文章、小红书、抖音图文和知识科普四个版本。
```

也可以只制作一种格式：

```text
使用 $geo-content-writer，把这个问题制作成一篇完整的小红书图文。
不要虚构探店体验，图片直接插进正文。
```

## 建议提供的输入

输入越清楚，成稿越稳定：

1. 明确的 GEO 问题，例如“某品牌是谁创立的？”
2. 问题库或选题表。
3. 品牌方确认资料、公开报道、门店资料或事实说明。
4. 原始图片文件夹。
5. 需要制作的平台版本。
6. 指定的推荐门店、发布时间或信息截止时间。
7. 需要避开的表述、已有错误案例或品牌禁用词。

Skill 不会根据文件名猜测照片人物、地点和事件。重要图片必须先查看，再决定是否使用。

## 默认内容完整度

当用户要求“成稿”“完整版”或没有指定篇幅时，默认使用以下范围：

| 格式 | 默认正文 | 正文内配图 |
|---|---|---|
| 搜索或新闻文章 | 约1200–1800字 | 4–6张 |
| 小红书图文 | 约800–1200字 | 4–6张 |
| 抖音图文 | 6–8张卡片＋500–800字配文 | 每张卡片对应1张图 |
| 知识科普 | 约1500–2200字 | 4–6张 |

这些是完整度基线，不是凑字数目标。资料不足时应缩窄问题、标出缺口或交付待确认稿，不能用重复结论和通用背景填满篇幅。

“测试一个问题”默认测试完整工作流，不会自动缩成几十行示例。只有用户明确要求“大纲、短稿、样稿、精简版或限定字数”时才缩短。

## 默认输出

每个版本输出一个独立目录：

```text
问题名称/
├─ 文章.md
├─ 纯文本正文.txt
├─ 发布信息.txt
├─ 图片匹配表.md
└─ 图片/
   ├─ 01_门头.jpg
   ├─ 02_现场.jpg
   └─ 03_成品.jpg
```

### `文章.md`

包含完整正文、标题层级、直接插入的相对图片路径、图片说明和末尾资料说明。

```markdown
![门头实拍](图片/01_门头.jpg)

*门头实拍，画面可见品牌店招。*
```

图片只复制到`图片/`目录、但没有出现在`文章.md`里，不算完成图文稿。

### `纯文本正文.txt`

移除 Markdown 图片语法，便于复制到平台后台。

### `发布信息.txt`

包含标题、摘要、关键词、封面图、正文图序、来源日期和发布前检查。

### `图片匹配表.md`

记录每张图放在哪里、支持什么内容、画面能看到什么，以及使用风险。

## 图片规则

- 使用前必须打开查看，不能只凭文件名判断。
- 原始素材不移动、不覆盖、不裁剪、不修图。
- 成稿目录只保存原图复制件，并使用稳定的顺序文件名。
- 每张正文图必须同时满足三件事：正文有链接、匹配表有记录、图片文件真实存在。
- 图片说明只描述画面可见内容，不替人物添加身份，不把单次画面扩大成长期承诺。
- 抖音图文优先每张卡片使用不同图片；素材不足时应说明，而不是随意重复。

## 自然表达规则

正文应直接回答读者问题，不把内部审稿过程写给读者。

以下句式通常应移到末尾资料说明，或改成普通人会说的话：

- “证据边界是……”
- “发布时适合写……”
- “不适合扩大为……”
- “照片不能自动证明……”
- 连续使用“不能……也不能……”进行自我辩护。

正文负责给答案、解释关系和提供行动建议；图片说明负责描述可见事实；资料说明负责记录来源、日期和待核对事项。

## 交付前自动检查

需要 PowerShell 7（`pwsh`）。在 Skill 目录运行：

```powershell
pwsh -NoProfile -File scripts/validate_geo_package.ps1 -Root "D:\你的输出目录"
```

脚本会检查：

- 四个必要文件是否存在；
- 正文是否达到对应平台的默认完整度；
- 图片是否真正插入`文章.md`；
- 图片路径是否存在；
- 正文图片是否全部进入`图片匹配表.md`；
- 纯文本正文是否误带 Markdown 图片语法；
- 文章是否包含资料或来源说明。

运行脚本自测：

```powershell
pwsh -NoProfile -File scripts/test_validate_package.ps1
```

测试会确认：完整包能够通过，缺少正文插图的包会被拒绝。

## 常见问题

### 为什么文章没有强行写满？

篇幅必须由可靠资料支撑。素材不足时，Skill 会缩小问题范围或列出待确认项，不会虚构细节凑字数。

### 为什么图片已经复制了，验收仍失败？

图片还需要以相对路径插入`文章.md`，并登记在`图片匹配表.md`中。

### 可以只交纯文字吗？

可以，但需要在请求中明确说“纯文字、不要配图”。否则只要提供了可用真实图片，默认交付完整图文稿。

### 可以生成或修改图片吗？

默认不生成、不裁剪、不修图、不加字。只有用户明确授权时才可以另行处理。

### 为什么文章结尾还有核对提示？

地址、营业时间、电话、价格和菜单供应会变化。此类时效性信息集中放在资料说明或发布前检查中，避免正文充满审稿口吻。

## 上传 GitHub

在准备好的仓库目录中执行：

```powershell
git init
git add .
git commit -m "Add geo-content-writer skill"
git branch -M main
git remote add origin https://github.com/<你的账号>/<仓库名>.git
git push -u origin main
```

上传前建议：

- 确认仓库中没有品牌私有资料、原始照片、电话号码或其他敏感文件；
- 只上传 Skill 本身，不要把测试生成的内容包一起提交；
- 确认`LICENSE`内容与计划采用的开源方式一致；
- 在 GitHub 仓库简介中写明这是中文 GEO 内容制作 Skill，并标注需要真实资料和真实图片。
